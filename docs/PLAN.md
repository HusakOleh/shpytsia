## 1. Мета й обсяг

**Мета.** Сайт бренду ШПИЦЯ (Львів, Новий Львів), який:
1. продає оренду електровелосипедів курʼєрам (Bolt / Glovo / Raketa) і ремонт велосипедів та електровелосипедів;
2. показує каталог велосипедів — характеристики, ціни, доступність — з Google-таблиці, без ручного оновлення сайту;
3. за один клік веде клієнта в Telegram (бронювання й підтвердження — там).

**Входить у MVP**
- Лендінг `/` — оренда й ремонт на одній сторінці.
- Каталог `/katalog` — картки з фото, характеристиками, цінами та статусом доступності; фільтри.
- Сторінка велосипеда `/katalog/[id]`.
- Дані — з Google-таблиці (через дзеркало), фото — з Google Drive; сайт оновлюється сам після змін у таблиці.
- CTA в Telegram з готовим текстом про конкретний велосипед; дзвінок.
- SEO-база, GA4, деплой на Firebase Hosting, CI/CD, інструкція для власників.

**Не входить у MVP:** онлайн-бронювання й оплата, форми зі сповіщеннями (потрібен серверний код), акаунти, магазин запчастин, англійська версія, блог, власний Telegram-бот (сайт лише готовий перемкнути CTA на бота, коли той зʼявиться). Сайт не збирає персональних даних: форм немає, cookies — лише GA4.

**Критерії успіху**
- Зміна статусу в таблиці зʼявляється на сайті ≈ за 10 хв (ціль; механізм — §3.3).
- Lighthouse (mobile) ≥ 90 за Performance, Accessibility, Best Practices, SEO.
- З будь-якої сторінки в Telegram — один клік.
- Власники додають велосипед або міняють статус без розробника.
- Інфраструктура — 0 грн/міс.

## 3. Архітектура

### 3.1 Схема

```
Олег / Макс ──правлять──► МАЙСТЕР-ТАБЛИЦЯ (приватна: «Велосипеди», Клієнти, Опл., Доступи…)
                                   │
                                   │ IMPORTRANGE — лише публічні колонки
                                   ▼
                          ДЗЕРКАЛО «ШПИЦЯ · Сайт», аркуш Bikes
                          Apps Script кожні 5 хв: оновити → змінилось? → запустити збірку
                                   │                                  ▲
                 workflow_dispatch │                                  │ Sheets API (лише читання,
                                   ▼                                  │ сервісний акаунт site-builder)
                          GITHUB ACTIONS ─────────────────────────────┘
                          sync → валідація → фото з Drive (sharp → WebP)
                          → next build (static export) → firebase deploy
                                   │            ▲
                                   │            └── Drive API ── папка «Фото велосипедів»
                                   ▼
                          FIREBASE HOSTING (Spark, CDN, SSL)
                          /  ·  /katalog  ·  /katalog/[id]
                                   │
                                   ▼
                          Відвідувач (переважно з телефона)
                                   │ «Забронювати»
                                   ▼
                          Telegram Макса (згодом бот) · дзвінок
```

### 3.2 Потік даних
1. Власник змінює рядок в аркуші «🚲 Велосипеди» майстер-таблиці.
2. Формула IMPORTRANGE у дзеркалі тягне лише публічні колонки (§4.4).
3. Apps Script у дзеркалі (раз на 5 хв, 07:00–23:00) примусово оновлює дзеркало, рахує хеш даних і, якщо він змінився, викликає `workflow_dispatch` у GitHub.
4. GitHub Actions:
   - `sync-catalog` читає дзеркало через Sheets API і валідує рядки;
   - нові фото завантажує з Drive, стискає у WebP і кешує;
   - `next build` робить статичний експорт у `out/`, далі деплой на Firebase Hosting. CDN Firebase скидається з кожним деплоєм.
5. Відвідувач отримує готовий HTML з актуальними статусами й бачить «Наявність оновлено: ДД.ММ о ГГ:ХХ».

### 3.3 Свіжість даних

```
правка в майстрі ──(≤ 5 хв: тригер скрипта)──► dispatch ──(≈ 3 хв: збірка й деплой)──► сайт
```

- **Ціль:** ≤ 10 хв від правки до сайту.
- **Чому потрібен скрипт.** Google документує, що IMPORTRANGE:
  - оновлює *відкриті* документи-отримувачі;
  - перевіряє оновлення щогодини, *поки документ відкритий*;
  - перезавантажується, коли документ відкривають.

  Поведінку закритого документа не описано. Дзеркало зазвичай ніхто не відкриває, тож без примусового оновлення збірка може годинами читати застарілі дані.
- **Spike (Етап 3.0)** перевіряє два способи наповнення дзеркала:
  - **А (основний, залишає IMPORTRANGE):** скрипт змінює параметр формули → IMPORTRANGE перечитує джерело.
  - **Б (запасний):** скрипт сам копіює публічні колонки з майстра в дзеркало значеннями. Дзеркало лишається, для власників нічого не змінюється, змінюється лише спосіб наповнення.

  Обираємо той, що надійно дає свіжі дані, і записуємо в журнал (§13).
- **Страховка:**
  - cron у GitHub Actions щогодини вдень перезбирає сайт, якщо дані змінились;
  - пункт меню «Сайт → Оновити зараз» у дзеркалі — для термінових змін (саме відкриття дзеркала теж оновлює IMPORTRANGE).
- **Чесно перед клієнтом:** на каталозі видно «Наявність оновлено: 31.10 о 14:05», біля кнопки — «Точну наявність підтвердимо в Telegram».

### 3.4 Обробка помилок

| Ситуація | Що відбувається |
|---|---|
| Google API недоступний або немає доступу (у CI) | збірка падає → деплою немає → на сайті лишається попередня версія; GitHub надсилає лист про збій |
| Немає обовʼязкової колонки (перейменували заголовок) або в дзеркалі `#REF!` / `#N/A` | збірка падає з поясненням, що саме не так |
| Після валідації 0 велосипедів | збірка падає — захист від порожнього каталогу |
| Рядок без `ID`, назви чи ціни за тиждень | рядок пропускаємо, попередження в підсумку збірки; решта публікується |
| Невідомий статус (наприклад, «вілний») | велосипед показуємо з нейтральним «Уточнюйте наявність» + попередження |
| Фото недоступне (не в спільній папці, видалене) | плейсхолдер + попередження |
| Apps Script не спрацював або закінчився термін дії токена | спрацює щогодинний cron; Google надсилає лист про збій тригера |
| Перевищено місячний ліміт трафіку Spark | сайт вимикається до кінця місяця → бюджет ваги сторінок і моніторинг (§11) |
| Локальна розробка без ключів | `CATALOG_SOURCE=fixtures` — тестові дані з репозиторію |

### 4.2 Схема аркуша «🚲 Велосипеди» (майстер)

Правила:
- один рядок — один велосипед;
- заголовки — в одному рядку, символ у символ як нижче (сайт шукає колонки за назвою, порядок не важливий);
- без обʼєднаних клітинок у тілі таблиці.

Наявні колонки `№`, `Власник`, `Telegram`, `Нотатка` лишаються в майстрі й у дзеркало не потрапляють.

| Колонка | Обовʼязк. | Значення | Приклад | Де на сайті |
|---|---|---|---|---|
| `ID` | ✅ | латиниця, цифри, дефіс; унікальний; **не змінювати** після публікації | `jamis-1` | URL `/katalog/jamis-1` |
| `Модель` | ✅ | текст | `Jamis Allegro` | назва картки |
| `Категорія` | ✅ | `Електро` · `Електро+акумулятор` · `Звичайний` | `Електро` | бейдж, фільтр |
| `Статус` | ✅ | `вільний` · `заброньований` · `в оренді` · `сервіс` (глосарій; регістр не важливий) | `вільний` | доступність |
| `Вільний з` | — | дата `ДД.ММ.РРРР` | `12.11.2026` | «звільниться орієнтовно 12.11» |
| `грн/тиждень` | ✅ | число | `1500` | ціна |

| `Запас ходу, км` | — | текст або число | `50–60` | характеристика |
| `Макс. швидкість, км/год` | — | число | `35` | характеристика |

### 4.4 Формула дзеркала (шаблон, перевіряємо в Етапі 3.0)

У клітинці `Bikes!A1` дзеркала (українська локаль, роздільник `;`):

```
=LET(
  src; IMPORTRANGE("<посилання на майстер>"; "'🚲 Велосипеди'!A2:Z300");
  hdr; CHOOSEROWS(src; 1);
  col; LAMBDA(name; CHOOSECOLS(src; MATCH(name; hdr; 0)));
  HSTACK(
    col("ID"); col("Модель"); col("Категорія"); col("Статус"); col("Вільний з");
    col("грн/тиждень"); col("грн/місяць"); col("Мотор, Вт"); col("Акумулятор");
    col("Запас ходу, км"); col("Макс. швидкість, км/год"); col("Колеса"); col("Рама");
    col("Гальма"); col("Комплектація"); col("Опис"); col("Фото"); col("На сайті"); col("Порядок")
  )
)
```

- Діапазон починається з `A2`, бо в рядку 1 майстра декоративний заголовок, а назви колонок — у рядку 2.
- Колонки вибираємо **за назвою**:
  - переставлені колонки в майстрі нічого не ламають;
  - колонка, якої немає в переліку, у дзеркало не потрапить;
  - перейменована колонка з переліку дає `#N/A`, і збірка падає з поясненням.
- Першого разу власник натискає «Надати доступ»: дозвіл IMPORTRANGE діє між цими двома таблицями.

### 4.5 Фото
- Завантажувати лише в папку «ШПИЦЯ · Фото велосипедів» (вона спільна з сервісним акаунтом). Посилання на файл в іншому місці дасть плейсхолдер.
- Формат: JPG / PNG / WebP з телефона, бажано горизонтальні 4:3, велосипед збоку на чистому фоні (рекомендації з `directions/rental/ads/rental.md`). 3–5 фото на велосипед.
- Замінити фото = завантажити новий файл і замінити посилання (готові варіанти кешуються назавжди).
- Збірка генерує WebP шириною 320 / 640 / 960 / 1280 px з хешем у назві й кешує результат між збірками. Пропорції беремо з метаданих — верстка не «стрибає».

### 4.6 Валідація й нормалізація (покриваємо тестами)
- Пробіли й регістр: `Вільний` = `вільний`; ` так ` = `так`.
- Числа: `1500`, `1 500`, `1 500 грн.`, `1500,00` → `1500`.
- Порожні `ID`, `Модель` або `грн/тиждень` → рядок пропускаємо. Порожній або невідомий `Статус` → «Уточнюйте наявність». Порожня або невідома `Категорія` → велосипед видно лише у фільтрі «Усі». В усіх випадках — попередження.
- Дати: `ДД.ММ.РРРР` і серійні числа Sheets → ISO.
- Фото: ID дістаємо з посилань `drive.google.com/file/d/<id>/…`, `open?id=<id>`, `uc?id=<id>`; дублікати прибираємо.
- `ID`: дублікат → другий рядок пропускаємо; недопустимі символи → попередження.
- Усі попередження — у підсумку збірки GitHub (Job Summary), із номером рядка.

### 6.5 Firebase Hosting (`firebase.json`)
- `public: "out"`, `cleanUrls: true`, `trailingSlash: false`.
- Кешування:
  - `/_next/static/**` і `/img/**` (у назвах файлів хеш) → `public, max-age=31536000, immutable`;
  - усе інше (HTML, RSC, JSON) → `no-cache`: браузер перевіряє ETag і за потреби отримує нову версію; CDN Firebase очищується з кожним деплоєм.
- `404.html` генерує Next.
- У налаштуваннях Hosting обмежити кількість збережених релізів (наприклад, 20), щоб не впертися в 10 ГБ сховища.

### 6.6 GitHub Actions
- **`ci.yml` (кожен PR):**
  1. lint → typecheck → unit-тести;
  2. `sync` (з секретами — реальні дані, без них — фікстури);
  3. build → e2e smoke на `out/`;
  4. деплой у preview-канал (посилання зʼявляється в PR).
- **`deploy.yml`:**
  - тригери: push у `main`; `workflow_dispatch` (кнопка в GitHub або Apps Script); `schedule` — щогодини вдень (cron у UTC).
  - кроки:
    1. `sync`;
    2. для запусків за розкладом і через dispatch — порівняти хеш даних із `/_meta/version.json` живого сайту; якщо однаково — завершити без деплою;
    3. build → deploy live → підсумок (кількість велосипедів, попередження, посилання).
  - `concurrency`, щоб деплої йшли по черзі.
- Репозиторій публічний, тож хвилини Actions безкоштовні. Але GitHub вимикає `schedule` після 60 днів без активності в репозиторії; тоді увімкнути вручну або додати keepalive-крок. Cron тут лише страховка.

### 6.7 Git-процес і «готово»
- `main` — продакшн. Робота в гілках `feat/…`, `fix/…`, `chore/…` → PR → CI + preview → merge.
- Коміти — Conventional Commits (`feat: …`, `fix: …`, `docs: …`).
- **Definition of Done задачі:**
  - lint, typecheck, тести й build зелені;
  - preview переглянуто з телефона;
  - чекліст у цьому плані оновлено;
  - нові рішення — у журналі (§13).

## 7. Робота з Lovable

### 7.1 Що важливо знати
- Lovable генерує **не Next.js**. Нові проєкти з 13.05.2026 — TanStack Start (React, SSR), старіші — React + Vite. Компоненти (React + Tailwind + shadcn/ui) переносяться в Next.js майже без змін; маршрути, head-теги й серверні функції переписуємо.
- Git-синхронізація Lovable **створює новий репозиторій** (наявний підключити не можна) і синхронізує його в обидва боки на активній гілці. Перейменування чи переміщення репозиторію ламає синхронізацію.
- Отже, **два репозиторії:**
  - `shpytsia-design` — пісочниця Lovable;
  - `shpytsia` (цей) — продакшн-код на Next.js.

### 7.2 Процес
1. 👤 Створити проєкт у Lovable (рекомендація — акаунт veloshpytsia), підключити GitHub → новий репозиторій `shpytsia-design` (може бути приватним).
2. Спитати в чаті Lovable «What stack is this project on?» і записати відповідь у журнал (фреймворк, версія Tailwind).
3. Пройти промпти з Додатка А **по одному**, після кожного — перевірка на телефоні.
4. Ревʼю за чеклістом §7.3 → правки → погодження Максом і Олегом.
5. Заморозити: тег `design-v1` у `shpytsia-design`.
6. 💻 Перенести в Next.js за Додатком Б (Етап 5).
7. **Після перенесення джерело правди — код у `shpytsia`.** Нові зміни дизайну робимо в Lovable на тих самих моках, а переносимо лише змінені компоненти (диф між тегами `design-vN`). Дрібні правки — одразу в Next.js.

**Чому JSON-ключ прийнятний.** Сервісний акаунт бачить лише дзеркало (публічні колонки) і фото, тобто те, що й так опубліковано на сайті. Витік ключа не відкриє клієнтів, оплат чи доступів. Ключ зберігаємо лише в GitHub Secrets і локально в `.secrets/`; при підозрі на витік — перевипускаємо.

Також: 2FA на veloshpytsia@gmail.com і на GitHub; доступи — у менеджері паролів (як у `channels.md`), не в таблиці.

**Ліміти й вартість**

| Сервіс | Безкоштовно | Що важливо |

- **Staging** (окремий канал Hosting для гілки `develop`), якщо preview-каналів PR стане замало.

## Додаток А. Промпти для Lovable

Вставляти **по одному**; після кожного — перевірка на телефоні й дрібні правки окремими промптами.

**Тип даних** (вставити разом з А.1):

```ts
export type BikeStatus = 'вільний' | 'заброньований' | 'в оренді' | 'сервіс';
export type BikeCategory = 'Електро' | 'Електро+акумулятор' | 'Звичайний';

export interface BikePhoto {
  src: string;    // URL зображення
  alt: string;
  width: number;  // оригінальні розміри — для aspect-ratio
  height: number;
}

export interface Bike {
  id: string;               // 'jamis-1' — частина URL /katalog/jamis-1
  name: string;             // 'Jamis Allegro'
  category: BikeCategory;
  status: BikeStatus;
  availableFrom?: string;   // ISO-дата, коли орієнтовно звільниться
  priceWeek: number;        // грн
  priceMonth?: number;      // грн
  specs: {
    motorW?: number;        // 500
    battery?: string;       // '48 В · 21 А·год'
    rangeKm?: string;       // '50–60'
    maxSpeedKmh?: number;   // 35
    wheels?: string;        // '26″'
    frame?: string;         // 'M'
    brakes?: string;        // 'дискові гідравлічні'
  };
  equipment: string[];      // ['ліхтарі', 'замок', 'багажник']
  description?: string;
  photos: BikePhoto[];      // перше — обкладинка
  order: number;
}
```

**А.1 — Контекст і правила**
> Ми робимо дизайн і фронтенд-прототип сайту «ШПИЦЯ»: оренда електровелосипедів для курʼєрів (Bolt, Glovo, Raketa) і ремонт велосипедів та електровелосипедів у Львові (район Новий Львів). Це лише прототип: компоненти потім перенесемо в Next.js, тому дотримуйся правил:
> - Тільки фронтенд. Не підключай Supabase, Lovable Cloud, авторизацію, бази даних, серверні функції, відправку форм.
> - Дані — моки: `src/data/bikes.ts` (8–10 велосипедів строго за типом `Bike` нижче: з усіма статусами, з фото й без, з ціною за місяць і без) і `src/data/site.ts` (контакти, тарифи, послуги ремонту, FAQ).
> - Компоненти презентаційні: усі дані через props, один компонент — один файл. Розділи лендінгу — `src/components/sections/`, каталог — `src/components/catalog/`, спільні — `src/components/layout/`.
> - Tailwind + shadcn/ui; кольори й шрифти — лише через CSS-змінні (токени), без HEX у компонентах. Іконки — lucide-react. Без важких бібліотек анімацій і каруселей.
> - Mobile-first (база 360 px): аудиторія — курʼєри з телефона, часто зі слабким інтернетом.
> - Увесь текст українською. Гроші: «1 500 грн/тиж», «5 300 грн/міс».
> - Доступність: контраст ≥ 4.5:1, видимі focus-стани, alt, семантичні теги, `prefers-reduced-motion`.
>
> *(далі — тип `Bike`)*

**А.2 — Дизайн-система**
> Створи дизайн-систему в стилі «сучасний е-байк: технологічно й чисто». Токени:
> - primary `#0F172A` (deep navy);
> - accent / CTA `#3A86FF` (electric blue);
> - secondary `#2B2B2B`;
> - фон `#F5F7FA`;
> - додатковий `#00C2A8` (mint).
>
> Статуси: вільний — зелений, заброньований — бурштиновий, в оренді й сервіс — сірий; бейдж завжди з текстом. Шрифти: заголовки Montserrat 700, текст Inter 400/500, обидва з кирилицею. Великі скруглення, мʼякі тіні, багато повітря, реальні фото. Компоненти: Button (primary CTA, secondary, ghost), Badge статусу, Card, Section, Container, Chip. Покажи сторінку-вітрину всіх компонентів.
>
> *(Якщо обрано іншу палітру — підставити значення з `shared/brand/colors.md`.)*

**А.3 — Лендінг `/`**
> Зроби головну сторінку з такими розділами (зверху вниз):
> 1. Шапка: текстове лого «ШПИЦЯ», меню «Оренда · Каталог · Ремонт · Контакти», кнопка «Написати в Telegram»; на мобільному — бургер-меню.
> 2. Hero: заголовок «Оренда електровелосипедів для курʼєрів у Львові», підзаголовок «Заряджені, обслужені, з ліхтарями й замком. Свій майстер поруч — ремонт без черг.», кнопки «Обрати велосипед» (на /katalog) і «Написати в Telegram», чипи «від {мінімальна ціна з моків} грн/тиждень», «Новий Львів», «Пн–Сб».

**А.4 — Каталог `/katalog`**
> Сторінка каталогу:
> - Заголовок «Каталог велосипедів», рядок «Наявність оновлено: 31.10 о 14:05» і підказка «Точну наявність підтвердимо в Telegram».

> - Сітка: 1 колонка на телефоні, 2 на планшеті, 3 на десктопі.
> - `BikeCard` (props: `bike: Bike`): фото 4:3 з бейджем статусу поверх, назва, категорія, до 4 характеристик з іконками (мотор, акумулятор, запас ходу, швидкість), ціни «1 500 грн/тиж» і «5 300 грн/міс» (місяць — якщо є), кнопка за статусом і посилання «Детальніше»:
>   - вільний → бейдж «Вільний» (зелений), кнопка «Забронювати в Telegram»;
>   - заброньований → «Заброньований» (бурштиновий) + «звільниться ~12.11», якщо є `availableFrom`; кнопка «Дізнатися, коли звільниться»;

>   - сервіс → «На обслуговуванні» (сірий), кнопка «Повідомити, коли звільниться».

**А.5 — Сторінка велосипеда `/katalog/:id`**
> Сторінка одного велосипеда, зверху вниз:
> - хлібні крихти (Головна › Каталог › Назва);
> - галерея фото зі свайпом на телефоні (без важких бібліотек);
> - назва, бейдж статусу, ціни за тиждень і місяць;

> - короткі умови оренди (завдаток або документ, що в комплекті);
> - кнопка за статусом (як у картці);
> - блок «Інші велосипеди» (3 картки).

**А.6 — Стани й перевірка**
> Перевір усі сторінки на 360, 768 і 1280 px. Додай стани: картка без фото (плейсхолдер з іконкою велосипеда), без ціни за місяць, з довгою назвою; порожній результат фільтра; 404. Переконайся, що в проєкті немає Supabase, серверних функцій і HEX-кольорів у компонентах.

## Додаток Б. Перенесення Lovable → Next.js

| У Lovable (TanStack Start) | У нас (Next.js) |
|---|---|
| `src/routes/__root.tsx` (layout, head) | `src/app/layout.tsx` + `export const metadata` |
| `src/routes/index.tsx` | `src/app/page.tsx` |
| `src/routes/katalog.tsx` | `src/app/katalog/page.tsx` |
| `src/routes/katalog.$id.tsx` | `src/app/katalog/[id]/page.tsx` + `generateStaticParams` |
| `<Link to="/katalog">` (`@tanstack/react-router`) | `<Link href="/katalog">` (`next/link`) |
| `head()` / meta маршруту | `metadata` / `generateMetadata` |
| компонент зі станом або обробниками подій | `'use client'` на початку файлу |
| `<img>` | `next/image` (наш loader) |
| CSS-змінні в `src/styles.css` | `src/app/globals.css` (`@theme`) |
| Google Fonts через `<link>` | `next/font/google` (`latin`, `cyrillic`) |
| моки `src/data/bikes.ts` | `CatalogRepo` (дані з таблиці) + `test/fixtures` |
| `src/data/site.ts` | `src/content/site.ts` |
| `createServerFn`, Supabase | не переносимо |
| `VITE_*` | `NEXT_PUBLIC_*` |

Назви файлів у Lovable можуть відрізнятися — орієнтуємось на фактичну структуру `shpytsia-design`.

## Додаток В. Інструкція для власників (чернетка → `docs/owners-guide.md`)

**Змінити статус.** Майстер-таблиця → аркуш «🚲 Велосипеди» → колонка `Статус` → вибрати зі списку. На сайті зміна зʼявиться ≈ за 10 хв. Якщо терміново — відкрити дзеркало й натиснути «Сайт → Оновити зараз».

**Додати велосипед**
1. Новий рядок; `ID` латиницею (`jamis-2`) — потім не міняти.
2. Заповнити `Модель`, `Категорія`, `Статус`, `грн/тиждень`, бажано — характеристики й `Опис`.
3. Фото — у папку «ШПИЦЯ · Фото велосипедів» → «Копіювати посилання» → у колонку `Фото` (кілька — кожне з нового рядка; перше — обкладинка).
4. `На сайті` = `так`.

**Прибрати з сайту.** `На сайті` = `ні`. Рядок не видаляємо — історія лишається.

**Не можна:**
- перейменовувати чи видаляти колонки;
- міняти `ID` опублікованого велосипеда;
- правити дзеркало руками.

**Сайт не оновився?**
1. Відкрити дзеркало: чи видно там зміну?
2. «Сайт → Оновити зараз».
3. GitHub → вкладка Actions → останній запуск `deploy`. Якщо він червоний — у підсумку написано, який рядок або колонка не так.
